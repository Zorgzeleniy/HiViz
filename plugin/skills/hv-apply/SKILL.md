# HiViz Apply Procedure

1. **Before-probes** (ask the user first; if the task brief explicitly pre-authorizes the probes, run them without asking). Probes are run by the constitution engine, not by hand — it asks, judges the answer with the test's markers and adds a negative control, so no verdict rests on your reading of an answer. Pick the rules the approved edits could silence: every `merge` and `rewrite`, every `delete` of a duplicate whose twin must keep the rule alive, and every row the user marked `probe-worthy`; at most 3 rules unless the user asks for more. For each, write `.hiviz/tests/<id>.toml` per the tests procedure (`core/TESTS.md` §2): `guards = "<file>: `<phrase of the line as it is NOW>`"`, an indirect `ask`, and `must_include_any` = words only the rule's substance contains (a word a refusal like "I have no directive about X" would repeat is a bad marker). Then run `python <hiviz>/constitution/run.py --tests .hiviz/tests --corpus <root of the files you edit> --harness <the CURRENT harness: claude | codex | omp | pi | cursor | opencode, or a command template with {ask}> --out .hiviz/probes-before.json`, from the project root. Tell the user the cost first: each rule is about 4 model calls (the question and 3 control runs).

2. **Backups**: every file about to be edited → `<file>.bak-<YYYYMMDD>` next to it.
3. **Apply exactly the approved edits.** Nothing of your own: no new lines, no reformatting of untouched lines, no improvements. Merges and relocations — precisely as decided. A row's `DECISION` rules: `yes` = do its verb, `as-condition: <text>` = do it only as the condition says, `no` / `keep` / empty = leave the line untouched. The `where` column names the file; edit exactly that path.
4. **After-probes**: where a rewrite or merge changed the guarded line, update that test's backticked phrase to the new wording (else the row says `ORPHANED`), and run the same command with `--out .hiviz/probes-after.json`. Compare per rule: `PASS` before and after = alive (its source may have moved — fine if the rule survives in the remaining location); `PASS` → `FAIL` = rule lost → restore that line from the backup; `UNPROVEN` = the probe could not tell, because the harness answers the same without the line — report it as exactly that, never as "alive" (a rule that is UNPROVEN both before and after was not binding through that line to begin with).
5. **Ledger**: append ONE line per approved decision to `.hiviz/ledger.jsonl`:
   `{"file": "<abs path>", "marker": "<line fragment>", "written_at": "<iso>", "model": "<current model>", "reason": "<audit id or user note>", "action": "deleted|rewritten|kept|merged"}`. This is what makes future `blame` instant and conflict arbitration mechanical.
6. **Verify (deterministic, no model)**: `python <hiviz>/apply/verify.py --decisions .hiviz/decisions.md [--scope <dir you edited under>]`. Run it as it is — do not read or re-implement it, its output is the verdict. It compares every edited file with its backup and checks that exactly the approved edits happened: rows decided `no` / `keep` / empty and every Kept-safe line unchanged, `yes` rows applied, nothing else removed, changed or added, a backup for every edited file (and none for a file no decision names), a ledger entry per approved decision. Row status: `OK` · `REVIEW` (a rewrite or an `as-condition` edit — show the user the listed new text, a machine cannot judge it) · `UNVERIFIABLE` (the quote was not found) · `FAIL`, each FAIL ending in an action: `restore` = put the file back from its `.bak-<date>` and report it, `apply` = an approved edit is missing, make it. Run it again until there is no FAIL. If an after-probe made you restore a line (step 4), verify lists that row as `apply` — keep the line and say why in the final report. `<hiviz>` = the hiviz engines dir, first that exists: `engines/` two levels above this skill's `SKILL.md` (plugin installs: `<skill dir>/../../engines`), `~/.hiviz/engines` (npm installer), or a hiviz repo checkout. It contains `apply/verify.py`.
7. **Constitution hook (offer, don't auto-do)**: for decisions that KEPT or REWROTE a `severity: critical` rule (safety, access, prod), offer to author a probe test in `.hiviz/tests/<id>.toml` per the tests procedure. One offer, user decides.
8. **Final report**: table file · bytes before→after · what was done · probe verdicts (PASS / UNPROVEN / FAIL, with the proof column) · the verify verdict (and every REVIEW edit); plus a `git diff` for review. Do not commit.
